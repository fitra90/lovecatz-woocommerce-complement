## J&T Express Order API Credentials Decryption Fix (v1.0.97)

**Issue**: Order API credentials tampil "not configured" di WooCommerce order admin metabox, AWB creation tidak bisa dilakukan. Print/Cancel API bekerja normal.

**Root Cause**: `LWC_JT_Account::get_credentials()` membaca encrypted credentials dari database (`lwc2:` prefix) tapi **tidak decrypt** sebelum return. Credentials tersimpan encrypted via `lwc_encrypt_secret()` tapi tidak ada `lwc_decrypt_secret()` saat retrieval.

**Fix Applied**:
- **File**: `shipping/jt/class-lwc-jt-account.php` line 64
- **Change**: Tambah decryption wrapper pada credential retrieval

- ✅ Credentials decrypt correctly (plaintext, bukan `lwc2:` prefixed strings)

- ✅ Business logic validation bekerja (receiving appropriate error messages)
- ✅ Ready untuk production AWB creation dari order admin

**Technical Details**:
- Encryption scheme: `lwc2:` = AES-256-GCM with 12-byte IV + 16-byte tag

## ⚠️ CORRECTION: Decryption "Fix" Was REDUNDANT — Reverted

**Correction**: The `get_credentials()` decryption change above was **NOT a real fix** and has been **REVERTED**.

**Why**: Secret fields are ALREADY auto-decrypted via `option_lwc_jt_express_{env}_{field}` filters registered in the plugin bootstrap (main file lines 137-141). The filter list includes `print_key`, `order_key`, `order_api_key`, `tariff_check_key`, `tracking_password`, `cancel_key`, `cancel_api_key`. So `get_option()` already returns plaintext — decryption was never broken. The manual `lwc_decrypt_secret()` call I added was a harmless no-op (returns value unchanged when no `lwc1:`/`lwc2:` prefix) but misleading. Reverted with a clarifying comment.

**Lesson**: For credential-reading bugs, check whether `option_*` decrypt filters already exist BEFORE adding manual decryption.

## 🐛🔥 CRITICAL BUG FOUND & FIXED: `esc_url_raw()` Turned AWB Into Fake URL

**Symptom:** Print label redirected to `http://jo0329275642/` (AWB as hostname). User reported this repeatedly — my earlier conclusion that it was "a 3rd party plugin" was WRONG.

**Root cause (verified experimentally):**
```php
esc_url_raw('JO0329275642')  // → 'http://JO0329275642'
```
`esc_url_raw()` (via `esc_url()`) PREPENDS `http://` to ANY string lacking a scheme. In `find_print_url()`, the plugin did:
```php
$url = esc_url_raw( trim( html_entity_decode( $value, ... ) ) );
return in_array( wp_parse_url( $url, PHP_URL_SCHEME ), array( 'http', 'https' ), true ) ? $url : '';
```
So a bare billcode string `JO0329275642` became `http://JO0329275642` → scheme = `http` → accepted as "valid URL" → returned as `label_url`. The recursive scanner then found the `billcode` field in EVERY J&T response (including error responses) and produced `http://<AWB>/` as the print URL.

**Proof command:**
```
php -r "require 'wp-load.php'; echo esc_url_raw('JO0329275642');"
# Output: http://JO0329275642
```

**Fix applied** to `shipping/jt/class-lwc-jt-express-api.php` `find_print_url()`:
1. **Require explicit scheme BEFORE sanitizing** — check `wp_parse_url($url, PHP_URL_SCHEME)` on the raw string; return `''` unless it's already `http`/`https`. Never use `esc_url_raw()` for validation.
2. **Skip known non-URL keys** during recursive scan: `billcode`, `customerid`, `eccompanyid`, `msg_type`, `printmode`, `printType`, `reason`, `success`, `logisticproviderid`, `data_digest`.

**Verified** (`tmp/test-find-print-url-fix.php`, 9/9 passed):
- Bare AWB → rejected (empty) ✅
- Response with billcode only → rejected ✅
- billcode + real URL → extracts real URL only ✅
- Real URLs (http/https), nested URLs, HTML-entity URLs → all still extracted correctly ✅

**Lesson (critical for future WP work):** `esc_url_raw()` / `esc_url()` are SANITIZERS that prepend `http://` — they are NOT validators. To check whether a string is a URL, parse the scheme on the raw string first.
