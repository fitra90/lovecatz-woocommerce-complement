## FedEx — declared customs value = invoice grand total (plugin 1.0.94)
Permintaan user: "custom values FedEx pakai angka total dari invoice". Dikonfirmasi lewat
pertanyaan: pilih **grand total invoice** dan **ikut diskon**.

- `LWC_FedEx_API::build_customs_detail()` dulu menghitung nilai dari item:
  `get_item_subtotal( $item, false, true ) * qty` (= harga barang **sebelum diskon, tanpa
  ongkir & pajak**), lalu `round_for_currency()` (yang ternyata `ceil()`) → order #32 (USD)
  mendeklarasikan 2.00 padahal invoice 259.00.
- Sekarang: helper baru **`LWC_FedEx_API::get_declared_value_total( $order )`** (public,
  satu-satunya sumber angka) mengembalikan `$order->get_total()` + filter
  `lwc_fedex_declared_value_total`. Dipakai untuk `commodities[0].customsValue`,
  `commodities[0].unitPrice` (= total/qty) dan `totalCustomsValue` — jadi ketiganya selalu
  konsisten, dan selalu sama dengan baris TOTAL invoice.
- Item selection sekarang **hanya** menentukan `quantity` + `weight` manifest, bukan nilai.
  Loop di `build_customs_detail()` disederhanakan: langsung akumulasi qty/weight (fallback
  lama dipertahankan: item tanpa berat = 0.5 kg flat, extra product = `max(0.01, berat*qty)`,
  tanpa item sama sekali = 1 PCS / 0.5 kg). Panggilan filter
  `lwc_fedex_commodity_country_of_manufacture` dihapus karena hasilnya memang selalu dibuang
  (commodity agregat selalu pakai `$base_country`) — output tidak berubah.
- Metabox FedEx dapat baris read-only **"Declared customs value"** (`wc_price()` dari helper
  di atas) supaya admin bisa cek angka sebelum buat AWB. Teks bantuan di metabox + FedEx
  Settings + PRD.md ikut disesuaikan.
- Verifikasi CLI (harness `tmp/`, sudah dihapus): order 80/79/41 → 20000/42222/42222 (match),
  order 32 → 259.00 USD (match), commodity == totalCustomsValue di semua kasus; order
  sintetis subtotal 200 + fee −50 → declared 150 (bukan 200); filter override → 999. Metabox
  render tanpa fatal (order 32 `$259`, order 79 `Rp42.222`).
- **Belum diputuskan:** partial shipment. Kalau hanya sebagian item dicentang, nilai yang
  dideklarasikan tetap grand total invoice (bukan proporsional). Tanyakan ke user kalau
  mereka mulai mengirim sebagian.

## FedEx — dimensi karton dibulatkan KE BAWAH (plugin 1.0.95)
Permintaan user: pembulatan dimensi saat cetak AWB harus ke bawah (sebelumnya ke atas).

- Helper baru `LWC_FedEx_API::floor_dimension_cm( $value )` = `max( 1, (int) floor( (float) $value ) )`.
  Dipakai di **dua** tempat: `normalize_package_override()` (validasi/normalisasi input admin)
  dan `build_override_package()` (yang benar-benar menulis `requestedPackageLineItems[].dimensions`).
  Ceil di `build_override_package()` sebenarnya redundan karena override sudah dinormalisasi,
  tapi tetap diseragamkan supaya aman kalau dipanggil dengan data mentah.
- **Berat tidak diubah** — tetap `round(..., 2)`. Hanya L/W/H yang di-floor. `units` tetap `CM`.
- Jalur estimasi dari produk (`cube_dimensions()`, dipakai kalau kolom dimensi dikosongkan)
  **masih `ceil()`** — sengaja dibiarkan karena itu angka perkiraan, bukan input operator.
  Tawarkan ke user kalau mau disamakan.- UI metabox langkah 3: `step="1" inputmode="numeric"` → `step="0.01" inputmode="decimal"` untuk
  L/W/H, plus teks bantuan "…any fractional dimension is rounded down." Input ini dikirim via
  AJAX (`fedex-order-admin.js` baca `.val()`), jadi `step` tidak pernah memblokir submit —
  tapi dengan `step="1"` field tampak invalid saat diisi desimal.
- Verifikasi CLI (harness `tmp/`, sudah dihapus): 30.9/20.5/15.99 → 30/20/15; 0.9/1.1/2.4 → 1/1/2;
  12.4/12.5/12.6 → 12/12/12; 100.999/1.001/3.5 → 100/1/3; hasil bertipe `int`; berat 3.456 tetap
  3.46; validasi lama (dimensi tidak lengkap / nol / negatif / tanpa berat) tetap menolak; payload
  order #32 jadi `length 30, width 20, height 15` (sebelumnya 31/21/16).

## FedEx — estimasi dimensi dari produk juga KE BAWAH (plugin 1.0.96)
Tindak lanjut catatan 1 di atas; user minta disamakan.

- `cube_dimensions()` (dipakai kalau kolom L/W/H dikosongkan, dan juga oleh rate quote
  checkout lewat `split_into_packages()`) sekarang `floor()`, bukan `ceil()`.
- **Jebakan presisi:** `pow( $v, 1/3 )` bisa mendarat sedikit di bawah akar eksak —
  `pow( 2197, 1/3 )` = 12.999999999999998, jadi `floor()` polos memotong 1 cm penuh
  (2197 = 13³ → 12, 1000 = 10³ → 9, 1000000 = 100³ → 99). Perbaikannya bukan epsilon,
  tapi koreksi integer: kalau `pow( $side + 1, 3 ) <= $volume_cm3` maka `$side++`.
  Verifikasi: 2197→13, 1000→10, 1728→12, 2744→14, 3375→15, 10648→22, 1000000→100 (kubik
  sempurna tetap eksak), 2500→13, 7→1 (bukan kubik, tetap di-floor), 0.5→1 (clamp),
  volume 0 / negatif → `null`.
- Order #32 (produk 10×10×10 cm, qty 2, volume 2000 cm³, akar 12.599) sekarang mengirim
  `length 12, width 12, height 12` (sebelumnya 13/13/13). Input manual tetap 30/20/15.
- Catatan efek samping: karena rate quote FedEx ikut memakai jalur ini, estimasi tarif
  checkout untuk order tanpa dimensi manual jadi sedikit lebih murah.
