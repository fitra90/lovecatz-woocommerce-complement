## Verifikasi berat & jarak pada kalkulasi tarif (change shipping)

Pertanyaan user: "apakah tariff sudah mengkalkulasi berat & jarak?" Dijawab dengan uji CLI
(`tmp/diag-weight-distance.php`, sudah dihapus) + pembacaan kode tiap kurir.

Temuan:
- **Berat: YA.** `build_order_package()` menyusun paket bergaya cart dari item order
  (qty × `get_weight()`, dikonversi ke kg). J&T Express `get_package_weight_kg()` = berat riil
  saja (min 0,01 kg). JNE (`Jneshof_Weight_Helper::calculate_weight_from_package`) =
  max(berat riil, volumetrik L×W×H/6000), min 0,1 kg. FedEx memecah paket per
  `lwc_fedex_max_package_weight_kg`. RaySpeed kg min 0,1.
- **Jarak: YA, tidak langsung.** Plugin tidak menghitung km; ia menerjemahkan alamat jadi
  kode rute milik kurir lalu bertanya ke API kurir. J&T mengirim `sendSiteCode` (kota asal) +
  `destAreaCode` (area tujuan dari `LWC_JT_Route_Mapper`); JNE pakai `destination.postcode`;
  FedEx kirim `recipient.address.postalCode/stateOrProvinceCode/countryCode`. Komponen jarak
  dihitung server kurir.
- **PENTING — J&T sandbox mengembalikan harga stub.** Uji 1/2/5/10/20 kg → 11111/22222/55555/
  111110/222220, dan Sukoharjo/Surabaya/Bandung semua 11111. Linear sempurna + tidak peduli
  tujuan = respons dummy sandbox. `lwc_jt_express_environment` = `sandbox`, dan
  `LWC_JT_Account::get_credentials('production')` kosong (sandbox cusName `PTSBIDDISTILLERS`).
  Jadi efek jarak tidak akan terlihat sampai kredensial produksi dipakai.
- `LWC_JT_Route_Mapper::resolve()` **wajib** punya district; tanpa itu selalu
  "not present in the official J&T mapping". District valid bisa diambil dari
  `wp_lwc_indonesia_regions` (`wc_state_code` + `city_key` + `district_key`).
- JNE tidak bisa dites dari CLI: "Kredensial Tidak Valid - Authorization header required".
- J&T Cargo `calculate_shipping()` kosong — memang tidak memancarkan rate (internal saja).

## Dua dunia kredensial J&T Cargo (penting, sering bikin bingung)

J&T Cargo punya **dua pasang** kredensial yang sumbernya berbeda; plugin mewajibkan keempatnya
(`LWC_JTC_API::get_missing_signing_credentials()`):

1. **Developer / Open Platform** — `apiAccount` + `privateKey`. Ini yang tampil di dashboard
   Personal Centre → 用户配置. Dipakai untuk header: `digest = base64(md5(bizContent + privateKey))`.
2. **Merchant / e-waybill** — `customerCode` + `customerPassword` (pwd). **Bukan** password login
   dashboard. Ini milik akun e-waybill merchant (yang punya saldo resi). Dipakai untuk digest di
   body (khusus `freight_calculation`) dan untuk endpoint `ess/balance` (saldo waybill).

Bukti dari kode: ada endpoint khusus `verify_waybill_account` => `vip/checkCusPwd`
("E-waybill Account Verification") — endpoint "check customer password" yang memang dipakai untuk
memvalidasi pasangan customerCode+pwd. Kalau pwd itu password login dashboard, endpoint ini tidak
perlu ada.

- `account number` di dashboard = email/login developer, BUKAN customerCode.
- `uuid` sandbox tidak perlu di-request: `SANDBOX_DEFAULT_UUID` otomatis dipakai bila kosong.
- `customer_password` di-input **plain text**; plugin hash sendiri dengan `PASSWORD_SALT`.
- Cara termurah menguji tebakan pwd: endpoint `E-waybill Account Verification` di konsol Sandbox.
