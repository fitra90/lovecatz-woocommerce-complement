# Blocksy Complement Plugin — Plan (2026-09-29)

## Context
User requested a Blocksy Free complement that replicates Blocksy Pro's Global Header
panel in `Appearance > Customize`. Reference screenshot shows Pro's element palette
(Account, Button 1/2/3, Cart, Color Switch, Compare, Contacts, Contact Block,
Divider 1/2, HTML, Logo, Menu 1, Wishlist) plus the drag-and-drop header builder
with Desktop / Tablet / Mobile layouts.

## Decisions (confirmed with user)
- **Plugin:** new separate plugin `lovecatz-blocksy-complement` (NOT merged into
  `lovecatz-woocommerce-complement`). Keeps WooCommerce integration concerns
  separated from UI/header concerns. Plugin is reusable on non-Woo sites.
- **Scope:** full element set + multiple header instances (per-page conditional).
  Highest ambition tier.
- **WooCommerce:** soft dependency — show element as enabled, hide gracefully if
  WC inactive. Plugin does NOT refuse to load without WC.
- **Theme for verification:** Blocksy + a new child theme for styling overrides
  (name TBD; possibly `ddistillers-blocksy-child` or `blocksy-child`).

## Technical approach (anchors)
- Use `blocksy:header:settings` filter to extend the element registry without
  forking the panel builder.
- Reuse Blocksy's hooks (`blocksy:header:offcanvas:*`, etc.) for output injection.
- Element base class:
  ```php
  abstract class LBC_Element {
      abstract public function get_id();
      abstract public function get_label();
      abstract public function get_icon();
      abstract public function register_options($options);
      abstract public function render($atts);
  }
  ```
- WC elements (Cart/Account/Wishlist/Compare) feature-detect with
  `class_exists('WooCommerce')` and short-circuit when absent.

# Promo checkout — mobile order summary dedup (2026-09-29)

## Problem reported
"Popup pemilihan promo (Kupon & promo) tidak tampil di mobile view" on the
checkout page.

## Root cause (not a display:none bug)
The checkout uses the **WooCommerce Checkout Block** (client-rendered React),
so the promo picker is injected by `promo/promo-dashboard.js`
(`getCheckoutCouponContainer()` → first `.wc-block-components-totals-coupon`,
then `couponArea.after(picker)`). The picker itself rendered fine on mobile.

The real issue: on mobile the checkout block renders **two** order summaries:
1. `wp-block-woocommerce-checkout-order-summary-block.checkout-order-summary-block-fill-wrapper`
   inside the actions block — this is the one that holds the promo picker.
2. The sidebar `wc-block-checkout__sidebar` order summary.

WooCommerce scopes its layout to `@container (max-width: 699px)` against
`.wp-block-woocommerce-checkout` (`container-type: inline-size`). Below that
breakpoint the sidebar gets `order:0` (renders **first**) and the main column
`order:1`. The sidebar title (`wc-block-components-checkout-order-summary__title`)
therefore shows as a bare "Order summary" heading at the top while its body
stays collapsed (`aria-expanded="false"`) — a redundant duplicate above the form.

## Fix
`promo/promo-dashboard.css` — hide the redundant top sidebar title on mobile,
using a **container query** (not a viewport media query) so it mirrors
WooCommerce's own breakpoint exactly and cannot desync in the mismatch zone
(e.g. a 720px viewport with a 690px container):

```css
@container (max-width: 699px) {
  .wc-block-checkout__sidebar .wc-block-components-checkout-order-summary__title {
    display: none !important;
  }
}
```

Selector must be a **descendant** combinator: the title is nested at
`.wc-block-checkout__sidebar > .wp-block-woocommerce-checkout-order-summary-block > .wc-block-components-checkout-order-summary__title`
(a direct-child `>` selector silently fails).

Plugin version bumped 1.0.89 → 1.0.90 (header + `LWC_VERSION`).

## Verification (headless Chrome, no WP-CLI)
- Mobile 390px: top "Order summary" heading gone; bottom summary with
  "Kupon & promo" picker + Subtotal/Pickup/Total intact before Place Order.
- Desktop 1440px: sidebar order summary unchanged (title, picker, totals all present).
- Local site URL is `http://localhost/ddistillers` (NOT `ddistillers.test`);
  `home`/`siteurl` options point there and `.htaccess` uses `RewriteBase /ddistillers/`.
- Test product 13 has `_lwc_minimum_quantity=2`, so `?add-to-cart=13&quantity=1`
  silently fails — always add `quantity=2` when building a test cart.

## Second fix — picker attached to a hidden container (JS)
`promo/promo-dashboard.js` → `getCheckoutCouponContainer()` now prefers the
first **visible** container (jQuery `:visible`) and only falls back to the
first match when nothing is visible.

Why it matters: React renders `checkout-order-summary-block-fill-wrapper`
whenever its own container width is `<= 700px`, while WooCommerce's CSS hides
that wrapper at `@container (min-width: 700px)`. At container width **exactly
700px** both are true, so the wrapper is in the DOM but `display:none`. The old
"first match" logic attached the picker there → invisible promo picker. The
visible-first lookup moves it to the sidebar coupon area instead.

| viewport | container | fill-wrapper | picker location | picker visible |
|---|---|---|---|---|
| 390  | 343 | rendered, visible | fill-wrapper | yes |
| 768  | 691 | rendered, visible | fill-wrapper | yes |
| 775  | 698 | rendered, visible | fill-wrapper | yes |
| 777  | 699 | rendered, visible | fill-wrapper | yes |
| 778  | **700** | rendered, **display:none** | sidebar (JS fix) | yes |
| 779–1440 | ≥701 | not rendered | sidebar | yes |

Sidebar title hidden (`display:none`) only while container `< 700`, matching
WooCommerce's own mobile layout. Cart page (`/cart/`, block cart) verified at
390/768/778/1024/1440 — picker visible at every width, no regression.

## Verification tooling note
For computed-layout checks (not just DOM presence) on the React checkout block,
drive headless Chrome over the DevTools Protocol: launch
`chrome --headless=new --remote-debugging-port=9222 --user-data-dir=<tmp>`,
then use Node 22's built-in global `WebSocket` to call
`Emulation.setDeviceMetricsOverride` + `Page.navigate` + `Runtime.evaluate`.
`--dump-dom` alone cannot tell you whether a node is actually visible.
`--window-size` differs from `innerWidth` when a scrollbar appears — prefer the
emulation override for deterministic widths.

## ARCHITECTURE CORRECTION — 2026-09-29 (critical)
The Tahap 1 assumption was **wrong** and had to be reworked.

- `blocksy:header:settings` is NOT the element registry. It only supplies
  panel-level extra options (its default arg is `[]`). Using it adds nothing
  to the palette.
- Blocksy discovers header/footer items by **scanning directories**:
  `Blocksy_Customizer_Builder::get_registered_items_by()` globs
  `inc/panel-builder/{header,footer}/*` with `GLOB_ONLYDIR`, then applies
  `blocksy:{panel}:items-root-paths`. Each item directory must contain
  `config.php` (`$config`), `options.php` (`$options`, with `$panel_type`
  and `$prefix` in scope) and `view.php` (receives `$atts`, `$device`,
  `$item_id`, `$panel_type`, `$section_id`, `$row_id`, `$attr` via
  `blocksy_render_view()`'s `extract()`).
- **Do NOT** hook `blocksy:header:items-paths` with the parent directory:
  it is globbed, so every child directory is discovered regardless of
  availability. Append individual directories through
  `blocksy:header:items-root-paths` so `is_available()` stays authoritative.
- Fix shipped: `blocksy-header-items/<id>/{config,options,view}.php` shims
  that delegate to the element classes (single source of truth, no
  duplication). Registry became a singleton (`instance()`) because
  `view.php` is `require`d deep inside Blocksy with no plugin handle.

### Blocksy multi-header facts
- Blocksy Free **already** supports multiple header sections: the customizer
  JS has a `CREATE_NEW_SECTION` action producing ids `ct-custom-<rand>`.
  What Pro adds is conditional display. `LBC_Header_Instances` implements
  only that (context mapping + per-post override), which is the right scope.
- Item settings live inside the `header_placements` theme mod as a flat
  `items` list of `{ id, values }` per section — NOT as standalone theme
  mods. Read them via `LBC_Elements_Registry::get_item_values()`.
- `blocksy_get_theme_mod()` applies core's `theme_mod_{$name}` filter.
- `Blocksy_Header_Builder` memoises `section_value` / `current_section` in
  private props; there is **no** public `wipe_cache()`. Clear them by
  reflection if you must, and prefer injecting synthetic placements in
  memory over writing the theme mod.

## INCIDENT — test harness mutated the site's Blocksy header config
- A crashed run of the verification harness (fatal on a non-existent
  `wipe_cache()`) left `template`/`stylesheet` = `blocksy` AND wrote a
  modified `header_placements` into `theme_mods_blocksy`.
- The harness had overwritten `desktop / middle-row / end` with
  `[lbc-account, lbc-divider, lbc-color-switch]`.
- **Recovered** to Blocksy's own default `[menu, search]`. Evidence the
  default was correct: every other row/placement matched Blocksy's
  `get_default_value()` exactly, and the only deliberate customisation in
  `items` was a `text` element holding `[lwc_currency_switcher]` in
  `top-row/end`.
- Theme restored to `ddistillers`; plugin left inactive (as found).
- **Lessons (mandatory for future harnesses):**
  1. Never call `set_theme_mod()` in a test. Inject synthetic state via
     reflection and assert the DB is untouched.
  2. Wrap any theme switch in `register_shutdown_function()` so a fatal
     cannot leave the site switched.
  3. Verify restore explicitly at the end of every harness run.
