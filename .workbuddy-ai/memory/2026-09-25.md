## Desty Omnichannel REST export in IDR (review + fixes)

Reviewed the Desty REST conversion added to `LWC_Currency_Converter` and fixed
four gaps:

- `line_items[].price` (unit price, a float, not covered by WooCommerce's
  `format_decimal` list) was never converted — added, plus `taxes[].total` /
  `taxes[].subtotal` per item.
- Orders with no `_lwc_currency_base` / `_lwc_currency_rate` snapshot were
  exported unchanged (USD). Added a fallback to `get_base_currency()` +
  `get_rate_for( $currency )`, but only when `owns_currency_conversion()`
  (with an external converter the rate lives in the other plugin).
- Money output now uses `number_format( $v, 0, '.', '' )`; a float→string cast
  would emit scientific notation for very large IDR values.
- `is_desty_rest_request()` now guards `function_exists( 'wc_api_hash' )`.

### Verified facts (WooCommerce 11.1.1, HPOS on)
- DB stores the **hashed** consumer key: lookup is
  `WHERE consumer_key = wc_api_hash( $_GET['consumer_key'] )`, same as
  `WC_REST_Authentication::get_user_data_by_consumer_key()`. Plaintext keys
  arrive as `ck_…`. Auth sources: `consumer_key` query param, `PHP_AUTH_USER`,
  or `oauth_consumer_key` (HTTP, OAuth 1.0a).
- Filter is `woocommerce_rest_prepare_shop_order_object` (3 args) applied in
  `WC_REST_Orders_V2_Controller::prepare_object_for_response()`.
- `WOOC_REST_Orders_Controller` does **not** implement
  `prepare_item_for_response()`; call `prepare_object_for_response()` directly
  — it sets `$this->request` and `$this->request['dp']` itself.
- Rate direction confirmed: `lwc_currency_rates` `USD=15000` means
  1 USD = 15,000 IDR, so order-currency → IDR **multiplies** by the rate.

### Harnesses (tmp/, gitignored) — both deleted after verification
- `tmp/test-desty-rest.php` — pure unit check over a hand-built response.
- `tmp/test-desty-e2e.php` — builds a real USD order + two API keys
  (`Desty API`, `Mobile app`) inside `START TRANSACTION / ROLLBACK` and renders
  via the real controller. Result: 20,005 USD → 330,082,500 IDR for the Desty
  key, untouched USD for the other key.
- User does not want test files left behind in the plugin — delete them once the
  check passes. Still present from 2026-09-24: `tmp/test-order-number*.php`.
- **Trap**: do not re-instantiate the singleton (`instance()` + `init()`) inside
  a loop — the old callback stays hooked and the response is converted twice
  (16500²). Reset only the private `desty_rest_request` cache via reflection.

## JNE "Nama Pengirim (Pickup): tidak boleh lebih dari 50 karakter" (diagnosed + fixed)

Symptom: JNE request pickup / label flow returns
`Kesalahan Validasi - Nama Pengirim (Pickup): tidak boleh lebih dari 50 karakter`,
`success: false`. The user assumed it was the *order* (recipient) name.

Root cause: `pickup_name` is **not** an order name — it is
`Jneshof_Store_Helper::getStoreName()` → `get_bloginfo('name')`, i.e. the
WordPress site title. The live site (`ddistillers.com`) title is
`DDistillers.com - Producer & Exporter Essential Oils` = **52 chars**, over the
JNE middleware's 50-char cap. Local `blogname` is only `DDistillers Local` (17),
so the bug never reproduces on the Laragon install — check the live title, not
the local one. Confirmed via `https://ddistillers.com/wp-json/` → `name`.

- Only one code path builds `pickup_name`:
  `admin/includes/class-jne-admin-order-list.php` →
  `handle_request_pickup_action()` (~line 413).
- The same class **already truncates** the same value for CNote
  (`class-jne-admin-generate-cnote.php`: `olshop_shipper_name` → 30, receiver →
  30, goodsdesc → 60, addr chunks → 30). The pickup payload had no truncation —
  an oversight in JNE plugin 1.9.6, not a store-config problem.
- Also note `pickup_address` is built as `chunk[0] . ' ' . chunk[1] . ' ' . chunk[2]`
  where `getStoreAddress()` splits on 30-byte boundaries, so it can reach ~92
  chars and index warnings fire if the address yields < 3 chunks.

Fix applied to the third-party plugin (JNE 1.9.6):
`'pickup_name' => $this->truncate_string( ...getStoreName(), 50 )` plus a new
private `truncate_string()` (mirrors the CNote helper, uses `mb_strcut` so
multibyte chars are not split). Verified: 52 → 50, `php -l` clean.
**This patch lives outside our plugin and is lost on a JNE plugin update.**
Alternative fix needing no code: shorten the WP site title to ≤ 50 chars.

### Reverted (same day)
User confirmed the value really comes from the site name and fixed it by
shortening the site title, so the plugin patch was **removed** — JNE plugin is
back to pristine 1.9.6 (`pickup_name` line 413 unchanged, no `truncate_string`,
`php -l` clean). Lesson: do not patch this third-party plugin; the site title is
the supported knob and the fix survives plugin updates.

## FedEx item selection vs. label data (diagnosed, not yet fixed) — superseded by the section below

User report: "items cannot be selected correctly, the flow cannot continue to
label printing, and the item is not shown in the label-print data."

Two durable facts established by inspection (no code changed yet):

- **The FedEx label's `DESC1` = `customsClearanceDetail.commodities[0].description`.**
  Proved by decompressing `uploads/fedex-label-32-*.pdf` (ASCII85+Flate) — the
  text layer literally contains `AWB DESC1:Test Product DESC2: DESC3: DESC4:`.
  "Test Product" was the order line name under the OLD code
  (`'description' => wp_strip_all_tags( $item->get_name() )`); the working copy
  already sends `$label_description` there. So the metabox field
  `lwc_fedex_label_description` → `label_description` is the correct DESC1 knob,
  and `customsClearanceDetail` is only built when the destination country
  differs from the store base country.
- **The metabox and the create-shipment handler disagree about item coverage.**
  `render_metabox()` locks items from `item_ids` + `replaced_item_ids` of
  non-cancelled shipments; `lwc_fedex_create_shipment()` additionally refuses
  when any active shipment has empty `item_ids` (`has_unscoped_active_shipment`
  → "An active FedEx AWB does not identify its items"). Proved with a CLI probe
  on local order 32 (legacy shipment, `item_ids: []`): the metabox rendered the
  item **checked + enabled** with the create button enabled, but the server
  would always reject. Local order 32 is the repro fixture.
- `render_metabox()` renders the shipment contents as the **hardcoded**
  "Essential Oils" (`$shipment['contents']` is only used as an on/off flag), so
  the merchant can never see which items went on an AWB — `contents` is the
  `build_manifest_snapshot()` of `item_ids` + `extra_product_ids`.
- Fix direction: one shared coverage helper used by both the metabox and the
  AJAX handler; resolve items for display from `item_ids`/`extra_product_ids`
  (falling back to `contents`) instead of the hardcoded string.

## FedEx metabox: setup must precede AWB creation (follow-up, same day)

User pushback: "the AWB is already issued and I can only print; I want to set the
ship date, dimensions and weight **before** printing the label."

Answer that drives the design: **ship date, carton weight/dimensions and the
label description are request inputs.** FedEx bakes them into the label while
the AWB is created — the label text layer literally contains
`SHIP DATE: 26AUG26 … ACTWGT: 0.50 KG … AWB DESC1:…`, and the Ship API has no
update-label operation. So they can only be changed by cancelling the AWB and
creating a new one; there is no "set it after create" path.

Metabox changes:

- Reordered to the real sequence: `1. Scheduled ship date` → `2. Items in this
  FedEx package` → `3. Actual packed carton` → `4. FedEx label item description`
  → `Test rate quote` / `Create FedEx label`. The carton fieldset and the item
  list used to sit **after** the create button, which is what made the setup look
  optional/after-the-fact.
- Added an actions hint: steps 1-4 are sent to FedEx at create time; an issued
  AWB must be cancelled first.
- New `$blocking_awbs` in `render_metabox()`: when `! $can_create_label`, the
  blocked notice now renders one `Cancel AWB #N and start over` button per
  blocking AWB, reusing the existing `.lwc-fedex-cancel-shipment` handler
  (`data-shipment` index + `data-tracking`). AWBs without a tracking number are
  skipped because the cancel action cannot run for them.
- Ship-date hint now says it is printed as `SHIP DATE`.

Verified with `tmp/lwc-fedex-setup-order-verify.php` (deleted after the run, all
checks passed): DOM order of the four steps vs. the create button, cancel
shortcut index/tracking/label, no shortcut when nothing blocks, and regression
checks for coverage / manifest lines / DESC1 / custom weight+dims+ship date
reaching the payload. Harness trap: `disabled()` emits ` disabled='disabled'`
with its own leading space, so a needle like `id="x" disabled` fails — match the
tag with a regex instead.

Known remaining trap (explained to the user, not changed): the order-list
"Create shipment / AWB" button calls `lwc_fedex_create_shipment` with no
`manifest_mode`/ship date/carton, so it issues an AWB with today's ship date and
product-derived weight. Offer to redirect it to the order screen if the user
wants setup-before-create enforced everywhere.

## J&T Cargo — bug body digest, penyebab error 145003031 (v1.0.86)

Gejala dari user: `add_order` ke sandbox → HTTP 200, `code` = `145003031`,
`msg` = "Business parameter signature verification failed", dan balikan plugin
menampilkan `"content_digest_sent": false`.

**Akar masalah** (`shipping/jtc/class-lwc-jtc-api.php`, `signed_request()`):
`digest` (body signature) disisipkan ke `bizContent` hanya bila
`'freight_calculation' === $interface`. Padahal manual resmi
(`E:\Downloads\JTC_API_Integration_Manual_251208_121336 (1).pdf`) menandai `digest`
sebagai **required (Y)** pada 3.4.1 Create Order dan 3.4.2 Check Order. Aturan
umumnya: setiap payload yang membawa `customerCode` wajib menyertakan body signature.

**Perbaikan**: `digest` kini selalu disisipkan bila belum ada di payload (guard
`! isset( $data['digest'] )` sama seperti `customerCode`). Laporan
`content_digest_sent` kini dihitung dari `isset( $data['digest'] )`, bukan lagi
hardcode `freight_calculation`.

Catatan pendukung:
- Panjang digest base64 = **24 char**, bukan 30 seperti tertulis `String(30)` di
  manual. Itu batas maks; contoh PHP manual sendiri menghasilkan 24 (base64 dari
  16 byte raw MD5). Jangan "diperbaiki" jadi 30.
- Kode error lain yang muncul bersamaan: `145003100` (shipment_track),
  `145003080` (cancel_order, verify_waybill_account). Belum dipastikan, tapi
  kemungkinan satu akar yang sama (digest tidak dikirim).

**Environment — penting**: DB lokal `C:\laragon\www\ddistillers` tidak menyimpan
satu pun kredensial J&T Cargo (semua `lwc_jt_cargo_sandbox_*` UNSET), padahal user
sudah menerima respons API sungguhan. Jadi pengujian user berjalan di environment
**lain** (kemungkinan site live). Perbaikan kode harus di-deploy ke sana agar
berlaku; probe lokal hanya berguna untuk memeriksa kode, bukan kredensial.

Alat: `tmp/jtc-cred-status.php` (bootstrap wp-load.php) menampilkan status tiap
field, daftar field yang memblokir request, apakah uuid lolos `normalize_uuid()`,
dan contoh payload `add_order` yang akan dikirim. Tanpa mencetak nilai rahasia.

## Deteksi sukses bisnis J&T Cargo — diperlonggar (masih v1.0.86)

`evaluate_business_response()` sebelumnya **hanya** menganggap sukses bila
`code === '1'`. Manual mendokumentasikan `msg` = "Request status (success/fail)"
dan tidak pernah menyebut nilai `code` untuk sukses. Data nyata dari sandbox
memakai kode error 9 digit (`145003031`, `145003080`, `145003100`), jadi
bertaruh pada `'1'` itu berisiko: kalau sukses ternyata berkode lain, 3 hit tidak
pernah tercatat dan sertifikasi mandek walau signature sudah benar.

Kini sukses = HTTP 2xx **DAN** (`code === '1'` **atau** `strtolower($msg) === 'success'`).
`code` dan `msg` dibaca dulu, baru dievaluasi; pesan error tetap diambil dari
`msg` (fallback `message`). Kasus 2xx tanpa `code` dan tanpa `msg` tetap gagal
(structure change tidak dihitung sukses).

Diuji 9 kasus sebelum harness dihapus: code 1+success, code 0+success,
code 200+Success, ketiga error nyata di atas, 2xx tanpa code/msg, HTTP 500 + code 1,
dan konflik code 1 + msg fail (tetap true, karena code '1' eksplisit).
